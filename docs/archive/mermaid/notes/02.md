# PROJECT SYSTEM MAPPING + MERMAID ANALYSIS

## Goal

Build a concise, evidence-based map of the project from:

Business goals
→ users
→ product areas
→ workflows
→ data
→ AI/runtime architecture
→ integrations
→ security
→ deployment
→ verification

Then create the **smallest useful set of Mermaid diagrams** needed to improve:

- implementation accuracy
- dependency clarity
- testing
- security
- delivery sequencing
- cross-team understanding

Do not generate diagrams for completeness. Generate them only when they expose a real decision, dependency, workflow, risk, ownership boundary, or proof requirement.

---

# 1. Evidence-first project audit

Before diagramming, inspect the current project state.

Use the most authoritative evidence available:

1. current runtime/live state
2. current repository/code
3. Linear/project source of truth
4. database/schema/RLS
5. tests/CI
6. current official vendor docs
7. official GitHub examples
8. secondary sources only if necessary

Separate:

- ✅ verified fact
- 🟡 partially verified
- ⚠️ assumption
- ❓ unknown
- 🔴 contradiction/blocker

Do not invent missing architecture.

When documentation and code disagree, identify the conflict and state which source is authoritative.

---

# 2. Understand the business first

Identify:

- business purpose
- target users
- user problems
- business outcomes
- KPIs / measurable success
- core product areas
- highest-value workflows
- major integrations
- consequential actions
- major risks

Summarize the product in one sentence:

> `[User] uses [product] to [core job], assisted by [AI/system], producing [business outcome].`

---

# 3. Identify source-of-truth ownership

Before drawing architecture, explicitly state who owns what.

Example format:

| Concern | Source of truth |
|---|---|
| User identity | Supabase Auth |
| Tenant/business data | PostgreSQL/Supabase |
| AI orchestration | Mastra |
| Interactive AI UX | CopilotKit / AG-UI |
| Media | Cloudinary |
| Publishing | Postiz |
| Analytics | Metabase / PostHog / provider truth |
| Deployment | Vercel / Cloudflare where actually used |

Do not show duplicate ownership unless the architecture genuinely has it.

Flag unclear ownership as a risk.

---

# 4. Start with one overall system flow

Create one high-level Mermaid `flowchart`.

It must be understandable in under 30 seconds.

Use:

Business goal
→ user entry
→ major product areas
→ key workflows
→ AI/automation
→ durable data
→ external systems
→ measurable outcome

Keep it conceptual.

Do not include implementation-level components unless they are essential.

---

# 5. Choose diagrams by value, not by type

Before creating each diagram ask:

> Will this diagram expose a decision, dependency, security boundary, lifecycle, workflow, integration sequence, or verification requirement that is not already clear?

If no, skip it.

Recommended types:

| Mermaid type | Use when | Main benefit |
|---|---|---|
| `flowchart` | Product flow, workflow, dependencies, architecture | Finds missing steps and wrong sequencing |
| `journey` | Real role-based user experience | Keeps engineering tied to user outcome |
| `sequenceDiagram` | Auth, API, agent, tool, service interactions | Exposes call-order and boundary errors |
| `erDiagram` | Important entities and relationships | Prevents schema and ownership mistakes |
| `stateDiagram-v2` | Status/lifecycle transitions | Prevents invalid states |
| `requirementDiagram` | Requirement → implementation → proof | Prevents false “Done” |
| `gantt` | Real scheduling dependencies | Useful only for delivery planning |
| `gitGraph` | Release/branch complexity | Use only when Git flow itself is risky |
| `mindmap` | Unclear discovery space | Use only before architecture is settled |
| `timeline` | Migration/release history | Use only when chronology matters |

Do not generate every type.

---

# 6. Map the real users

Identify the 3–5 highest-value roles.

For each role define:

User
→ entry point
→ main job
→ AI assistance
→ decision/approval
→ durable data change
→ business outcome

Give one realistic example.

Example:

```text
Fashion operator
→ opens Shoot
→ asks Planner for production plan
→ AI drafts deliverables / shot list / budget
→ operator edits and approves
→ approved ShootPlan is saved
→ production can begin
